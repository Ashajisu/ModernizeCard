## 2. 적용 순서

1. `schema_alter_v2.sql` 실행 (v1 DDL 반영된 DB에 추가 적용)
2. 위 Java 파일들을 실제 프로젝트의 해당 패키지 경로에 복사
   - **패키지명 확인 필요**: `com.test.zoom.*`로 가정했습니다. 실제 루트 패키지가 다르면 일괄 치환하세요.
3. 메인 애플리케이션 클래스에 `@EnableScheduling` 추가 (없다면)
4. `CardTransactionProvider` 인터페이스 위치를 `com.test.zoom.service.CardTransactionProvider`로 가정하고 import 했습니다 — 실제 위치가 다르면 경로만 수정하면 됩니다.

## 3. 확인/보정이 반드시 필요한 항목

| 항목 | 내용 |
|---|---|
| **대출 현재 잔액** | `schema_alter_v2.sql`의 `loan.current_balance`를 원금(190,000,000)으로 초기화해뒀는데, 대출 시작일(2025.4.30)로부터 이미 약 15개월 지난 시점이라 **실제로는 원금보다 적게 남아있을 것**입니다. 지금까지 상환한 원금 누계(또는 최근 잔액증명서 상 잔액)를 알려주시면 정확한 값으로 다시 세팅해드릴게요. |
| **월상환액 검증** | `Loan.calculateMonthlyPayment(190000000, 2.75, 360)`으로 계산한 이론값과 실제 청구액(775,658원)이 맞는지 한번 계산 검증 권장 — 소수점 반올림 방식 차이로 몇백 원 오차 가능 |
| **자동차세 납부계좌** | `kb입출금`으로 임시 지정해뒀습니다 (schema_ddl.sql 참고) — 실제 계좌로 수정 필요 |
| **CardTransactionProvider 실제 구현체명/카드사 코드 문자열** | `KOOKMIN/SAMSUNG/SHINHAN/WOORI/NONGHYUP` 문자열이 실제 `getCardCompanyCode()` 반환값과 일치하는지 확인 필요 |
| **MEMBER_TAG 매칭 시 계정 처리** | 현재는 가족구성원 태그가 매칭되면 계정과목을 무조건 '미분류'로 두고 수동 확인을 유도합니다. 특정 가족구성원 태그일 때 항상 정해진 계정과목(예: 무조건 '쇼핑')으로 자동 분류하고 싶다면 `MerchantCategoryResolver`에 로직 추가 필요 |

## 4. 미확인(is_confirmed=false) 처리되는 전표 유형

- 2단계 계좌출금 정산 (`SettlementBatchService`)
- 모든 정기 분개: 적금이체, 고정지출(가족회비/자동차세), 대출상환 (`RecurringJournalBatchService`)

→ 확정 처리 API/화면(예: `PATCH /journal-entries/{id}/confirm`)은 아직 설계하지 않았습니다. 다음 단계에서 필요합니다.

GET	/journal/{id}	상세 조회
POST	/journal	생성

DELETE	/journal/{id}	삭제

dto 생성
autoGenerated는 Service에서 source != MANUAL 로 변환하면 됩니다.

JournalResponse 에서 차변/대변은 Service에서 SUM() 결과를 넣는 것을 권장합니다. BigDecimal로 유지해도 되지만, 화면 표시 시 포맷팅을 고려하면 문자열로 변환하는 방법도 있습니다.
추가로 추천하는 개선 사항

현재 JournalEntry.Source를 DTO에서도 그대로 사용하고 있는데, 장기적으로는 엔티티의 enum을 DTO에서 직접 참조하지 않는 것을 권장합니다.
예를 들어,
public enum JournalSource {
MANUAL,
CARD_IMPORT,
SETTLEMENT,
RECURRING
}
를 dto/journal 패키지에 별도로 두면, 엔티티 구조 변경이 API 계약에 영향을 주지 않아 계층 간 결합도가 낮아집니다.

또 하나는 JournalResponse의 debitAmount와 creditAmount는 금액 연산과 정렬을 고려하면 BigDecimal로 유지하는 것이 더 적합합니다. 화면에서만 천 단위 콤마 등의 포맷팅을 적용하는 편이 확장성과 유지보수 측면에서 유리합니다.


서비스 구조
JournalAssembler 담당 기능은 다음과 같습니다.
DTO → Entity 변환, Account 조회, JournalLine 생성, 차변/대변 합계 계산, Balance 검증
수기입력/카드분개/정기분개가 모두 동일한 검증을 거치게 됩니다.
